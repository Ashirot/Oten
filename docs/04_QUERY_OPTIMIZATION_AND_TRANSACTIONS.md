### PART 1: QUERY PROCESSING & OPTIMIZATION (Section D)

The project demonstrates two real-world query optimization scenarios using MySQL 8.0 `EXPLAIN FORMAT=TREE` and `EXPLAIN FORMAT=JSON`.

#### Optimization Example 1: Multi-Column Composite Indexing on Order Fulfillment
1. **Original SQL Query:**
   ```sql
   SELECT 
       o.order_number, 
       o.created_at, 
       o.order_status, 
       o.total_amount, 
       u.name AS customer_name
   FROM orders o
   LEFT JOIN users u ON o.user_id = u.id
   WHERE o.created_at >= '2026-01-01' 
     AND o.order_status = 'delivered';
   ```

2. **Explanation of what the query does:**
   Retrieves all delivered customer pastil orders within a specific date boundary for revenue and delivery fulfillment auditing, joining the users table to retrieve customer names.

3. **Execution Plan Before Optimization (EXPLAIN):**
   - **Access Type:** `ALL` (Full Table Scan)
   - **Cost Assessment:** Without composite indexing, MySQL must read every data block in the `orders` table and evaluate two separate `WHERE` conditions per row in memory.
   ```text
   -> Filter: ((o.created_at >= TIMESTAMP'2026-01-01 00:00:00') and (o.order_status = 'delivered'))
       -> Table scan on o  (cost=X rows=N)
   ```

4. **Optimization Technique Applied:**
   - **Technique:** Multi-Column Composite B-Tree Index on `(order_status, created_at)`.
   - **Rationale:** The equality check (`order_status = 'delivered'`) is placed first, followed by the range scan (`created_at >= ...`). In InnoDB's clustered B-Tree architecture, this allows MySQL's optimizer to jump directly to the exact index slice of 'delivered' records and iterate through only the matching date range, skipping unrelated orders completely.
   - **DDL:** `CREATE INDEX idx_orders_status_created ON orders (order_status, created_at);`

5. **Execution Plan After Optimization (EXPLAIN):**
   ```text
   -> Nested loop left join
       -> Index range scan on o using orders_order_status_created_at_index 
          over (order_status = 'delivered' AND '2026-01-01 00:00:00' <= created_at)
       -> Single-row index lookup on u using PRIMARY (id=o.user_id)
   ```

6. **Results & Performance Analysis:**
   - **Access Type:** Changed from `ALL` (Table scan) to `range` scan.
   - **Rows Examined:** Scaled down from $100\%$ of table rows to strictly the matching delivered rows.
   - **Conclusion:** While small demo tables show modest millisecond differences, as order history grows into tens of thousands of rows, this composite index eliminates disk I/O bottlenecks and prevents memory-intensive temporary table buffer allocations.

#### Optimization Example 2: Correlated Subquery Elimination via Indexed Grouped JOIN
1. **Original SQL Query:**
   ```sql
   SELECT 
       c.name AS category_name,
       (SELECT COUNT(*) 
        FROM products p 
        WHERE p.category_id = c.id) AS total_products,
       (SELECT COALESCE(SUM(oi.subtotal), 0.00) 
        FROM order_items oi 
        JOIN products p2 ON oi.product_id = p2.id 
        WHERE p2.category_id = c.id) AS category_revenue
   FROM categories c;
   ```

2. **Explanation of what the query does:**
   Computes the total number of menu products and gross sales revenue generated by each product category.

3. **Execution Plan Before Optimization (EXPLAIN):**
   - **Access Type:** `DEPENDENT SUBQUERY`
   - **Bottleneck:** MySQL executes the subqueries $N$ times (where $N$ is the number of categories). For each category row, it executes two nested index lookups and join scans.
   ```text
   -> Table scan on c
   -> Select #2 (subquery in projection; dependent)
       -> Aggregate: count(0)
   -> Select #3 (subquery in projection; dependent)
       -> Nested loop inner join
   ```

4. **Optimization Technique Applied:**
   - **Technique:** Subquery Elimination (Query Rewriting into a single linear `LEFT JOIN` with `GROUP BY`).
   - **Rationale:** Replacing nested correlated subqueries with a grouped join allows MySQL to stream through records in a single query pass, leveraging existing primary keys and foreign keys (`products.category_id` and `order_items.product_id`).

5. **Optimized SQL Query:**
   ```sql
   SELECT 
       c.name AS category_name,
       COUNT(DISTINCT p.id) AS total_products,
       COALESCE(SUM(oi.subtotal), 0.00) AS category_revenue
   FROM categories c
   LEFT JOIN products p ON c.id = p.category_id
   LEFT JOIN order_items oi ON p.id = oi.product_id
   GROUP BY c.id, c.name;
   ```

6. **Results & Performance Analysis:**
   - **Before:** Repeated $O(N)$ dependent subquery evaluations.
   - **After:** Single $O(1)$ query plan with `Nested loop left join` and streaming aggregation. Temporary filesorts for correlated expressions are eliminated, drastically cutting execution overhead.

### PART 2: TRANSACTION MANAGEMENT & CONCURRENCY (Section E)

#### 1. ACID Transaction Guarantees
- **Atomicity:** All statements inside an order checkout (`orders` insert, `order_items` insert, `products` stock decrement, and `inventory_logs` audit) execute as a single indivisible unit. If any step fails, all intermediate modifications are completely undone via `ROLLBACK`.
- **Consistency:** Database check constraints (`chk_product_stock`, `chk_order_total`) and triggers (`trg_prevent_negative_stock`) validate the integrity of every affected table before committing.
- **Isolation:** Transaction operations are isolated from concurrent sessions using InnoDB's `REPEATABLE READ` default isolation level and row-level pessimistic locking (`SELECT ... FOR UPDATE`).
- **Durability:** Committed transactions are flushed to InnoDB's Write-Ahead Log (WAL / redo log), ensuring that changes survive sudden system or power failures.

#### 2. Demonstration of Transaction Control (`COMMIT` and `ROLLBACK`)

##### A. Successful Transaction (COMMIT)
```sql
START TRANSACTION;

-- Step 1: Lock product row to verify stock
SELECT stock_quantity FROM products WHERE id = 1 FOR UPDATE;

-- Step 2: Insert order header
INSERT INTO orders (order_number, customer_name, total_amount, payment_method, order_status)
VALUES ('TX-SUCCESS-01', 'Maria C.', 240.00, 'cod', 'preparing');
SET @order_id = LAST_INSERT_ID();

-- Step 3: Insert line items (Trigger trg_after_order_item_insert automatically decrements stock)
INSERT INTO order_items (order_id, product_id, quantity, unit_price, subtotal)
VALUES (@order_id, 1, 2, 120.00, 240.00);

-- Step 4: Commit changes
COMMIT;
```
*Verification:* Order record is created, stock decreases from 85 to 83, and an inventory audit log is generated.

##### B. Aborted Transaction (ROLLBACK)
```sql
START TRANSACTION;

-- Step 1: Insert order header
INSERT INTO orders (order_number, customer_name, total_amount, payment_method, order_status)
VALUES ('TX-FAIL-02', 'Rollback User', 500.00, 'cod', 'preparing');

-- Step 2: Simulate invalid operation (attempt to drive stock negative)
-- Trigger trg_prevent_negative_stock fires and signals SQLSTATE '45000'
UPDATE products SET stock_quantity = -10 WHERE id = 1;

-- Application exception handler catches the trigger error and rolls back:
ROLLBACK;
```
*Verification:* `SELECT * FROM orders WHERE order_number = 'TX-FAIL-02'` returns 0 rows. The temporary order is removed, and product stock remains unaltered.

#### 3. Concurrency Issue & Resolution Demonstration

##### The Concurrency Problem: Lost Update / Race Condition Anomaly
- **Scenario:** Assume the popular "Family Pack" has only **1 unit** left in stock.
- Two customers (Customer A and Customer B) submit an order simultaneously at timestamp `T0`:
  1. **Time T0:** Session A reads `stock_quantity = 1` (valid).
  2. **Time T0 + 1ms:** Session B reads `stock_quantity = 1` (valid, based on stale read).
  3. **Time T0 + 2ms:** Session A completes order, updates `stock_quantity = 0`.
  4. **Time T0 + 3ms:** Session B completes order, updates `stock_quantity = 0 - 1 = -1` (Overselling!).

##### The Solution: Pessimistic Row-Level Locking (`SELECT ... FOR UPDATE`)
In Laravel, this is implemented as:
```php
$product = Product::lockForUpdate()->find($productId);
```
In MySQL raw SQL:
```sql
SELECT * FROM products WHERE id = 1 FOR UPDATE;
```
- **How it works:**
  1. Session A executes `SELECT ... FOR UPDATE`, placing an exclusive write lock (X-lock) on product ID 1.
  2. Session B executes `SELECT ... FOR UPDATE` for product ID 1. InnoDB halts Session B and places it in a lock-wait queue.
  3. Session A decrements stock from 1 to 0 and issues `COMMIT`, releasing the lock.
  4. Session B immediately resumes, reads the refreshed value `stock_quantity = 0`, detects insufficient inventory, and cleanly rejects the purchase without corrupting the database.
  5. As an additional fail-safe, `trg_prevent_negative_stock` prevents any rogue process from setting stock below 0.
